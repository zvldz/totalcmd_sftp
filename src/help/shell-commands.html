Shell Fallback - Command Reference

When SFTP/SCP are blocked, the plugin can use shell command pipelines for file transfers. This page documents the shell commands used.

Overview

Why Shell Fallback?

  • Some hosts disable SFTP subsystem
  • SCP may be restricted by administrator
  • Shell access often still available
  • Plugin uses standard Unix commands for transfer

When to Enable

  • SFTP connection fails with "Subsystem request failed"
  • SCP transfers fail with permission errors
  • Host policy blocks standard transfer methods
  • Enable: Use shell transfer (for blocked hosts)

Transfer Methods

With Use shell transfer (for blocked hosts) enabled, every transfer goes through base64 over the hidden interactive shell (Method 2). On an SCP-only session without that option, files go through scp (see SCP Shell Mode below), and a resumed transfer uses the raw stream (Method 1), switching to base64 when the raw stream fails.

Method 1: Raw cat Stream

Direct streaming over a separate exec channel:

Download

cat '/remote/path/file.txt' 2>/dev/null
tail -c +3001 '/remote/path/file.txt' 2>/dev/null   # resume after 3000 bytes
  • Outputs file content to stdout
  • Plugin captures and writes to local file
  • Fast, no encoding overhead
  • A size mismatch on a fresh download switches to base64; on a resumed one it is a failure

Upload

cat > '/remote/path/file.txt'
cat >> '/remote/path/file.txt'   # resume
  • Plugin sends file content to stdin
  • Shell redirects to target file; a non-zero exit status is a write error
  • The remote size is checked afterwards with wc -c < 'file'; a mismatch switches to base64

Method 2: Base64 Encoding

Most robust fallback for restrictive environments:

Download with Base64

test -r '/remote/path/file.txt' && base64 '/remote/path/file.txt' 2>/dev/null | fold -w 76
tail -c +3001 '/remote/path/file.txt' 2>/dev/null | base64 | fold -w 76   # resume
  • Encodes binary to ASCII
  • fold -w 76 keeps lines short (macOS base64 writes one line for the whole file)
  • Plugin decodes base64 locally, line by line
  • Handles any file type safely

Upload with Base64

printf '%s' '<base64 chunk>' | base64 -d > '/remote/path/file.txt'
printf '%s' '<base64 chunk>' | base64 -d >> '/remote/path/file.txt'
  • Plugin encodes file to base64, one command per chunk
  • The first chunk creates the file (>), the rest append (>>)
  • Chunks are 1024 bytes; for larger files the plugin first checks with a six-byte test whether the shell decodes base64 spread over several lines, and then sends 48 KB per command
  • Every chunk must answer exit status 0, and the final remote size is checked
  • Works through any text-only channel

Resume

Resume is byte-exact. Each base64 chunk is encoded and decoded on its own, padding included, so a transfer can continue at any byte without alignment and without sending bytes twice.

  • Download: tail -c +N starts right after the bytes already on disk
  • Upload: the remote size from wc -c is the offset; an unknown size, or one larger than the local file, refuses the resume
  • A text-mode transfer is never resumed; it starts over

Directory Operations

File operations on an SCP-only session run as shell commands. Names are single-quoted, with each quote inside written as '\''.

List Directory

env TZ=UTC0 LC_ALL=C TIME_STYLE=locale BLOCK_SIZE=1 LS_BLOCK_SIZE=1 QUOTING_STYLE=escape ls -la '/remote/path' | cat
  • Detailed listing with permissions; plugin parses output for file info
  • Fixed locale, UTC times and byte sizes, whatever the user's environment sets
  • With GNU ls, QUOTING_STYLE=escape escapes spaces, newlines and other unusual bytes, so each line is one entry; whether ls supports this is checked once, with the first listing

Create Directory

mkdir -m 755 '/remote/path/newdir'
  • -m The session's mode for new folders (default 755)
  • Fails if the folder already exists

Remove File

rm '/remote/path/file.txt' < /dev/null
  • A name that does not exist is reported as a failure
  • Input from /dev/null, so rm does not wait for an answer on a write-protected file

Remove Directory

rmdir '/remote/path/olddir'
  • Removes only an empty folder; Total Commander deletes the contents first
  • Whatever could not be deleted keeps the folder in place

Rename/Move, Copy

test -e '/remote/path/new.txt' || test -L '/remote/path/new.txt'
mv '/remote/path/old.txt' '/remote/path/new.txt'
cp '/remote/path/old.txt' '/remote/path/new.txt'
  • The test probe runs first unless overwriting was confirmed; an existing name goes back to Total Commander as "file exists"
  • Only exit status 0 counts as success

Change Attributes

chmod 644 '/remote/path/file.txt'

Get File Info

stat '/remote/path/file.txt'
  • Shown in the file properties

Shell Session

Shell Start

  • The hidden shell runs on a terminal opened with echo turned off
  • The plugin then sends exec /bin/sh (the commands are written for a POSIX shell; a csh, tcsh or fish login shell reads them differently) and stty -echo
  • A restricted shell that refuses exec keeps running, and the commands work as far as it understands them

Command Markers

echo "__WFX_DD_BEGIN__<random>"; <command>; echo "__WFX_DD_""END__<random>":$?
  • Each command is wrapped in begin and end markers with a random part, so its output is told from the terminal echo
  • The end marker is split by an empty string, so a terminal that still echoes never shows it whole
  • The exit status after the end marker decides success

SCP Shell Mode

SCP over an exec channel

On an SCP-only session without shell transfer, files go through the scp program on the server:

SCP Send

scp -t '/remote/path/file.txt'
  • -t Target mode (receive file)
  • Plugin sends file metadata + content
  • Server acknowledges each step

SCP Receive

scp -f '/remote/path/file.txt'
  • -f From mode (send file)
  • Server sends metadata + content
  • Plugin acknowledges receipt

SCP Shell Protocol

# Plugin sends:
C0644 1234 file.txt  (file mode, size, name)
[...file content...]
\0  (null terminator)

# Server responds with:
\0  (OK)
\1error  (Error)
\2fatal error  (Fatal)

Error Handling

Command Fails

  • A non-zero exit status (missing base64, read-only destination, full disk) is reported as an error
  • A failed raw transfer switches to base64

Permission Denied

  • Check remote file permissions
  • Verify user has write access
  • Try alternative location

Command Timeout

  • Each line of a command's output is waited for up to 10 seconds of silence, and at most 45 seconds in all
  • The limits apply per line, so a large base64 download of many lines is not cut off

Partial Transfer

  • Connection interrupted mid-transfer
  • Resume continues at the exact byte where the transfer stopped

Performance Considerations

Base64 Overhead

  • Base64 increases size by ~33%
  • Encoding/decoding CPU cost
  • One shell round-trip per upload chunk
  • Still faster than no transfer at all

Security Notes

Command Injection Protection

  • Every name is single-quoted; a quote inside is written as '\''
  • A command for the interactive shell that would contain a control character other than a newline (for example an escape in a file name) is not sent; the plugin reports that the name contains a control character. A newline in a name is sent inside its quotes
  • Commands run with the user's own permissions

Shell Quoting

# Filename with spaces:
cat '/remote/path/my file.txt'

# Filename with special chars:
cat '/remote/path/file$var.txt'

# Filename with a quote:
cat '/remote/path/it'\''s.txt'
Note: Shell fallback prioritizes compatibility over terminal semantics. Some interactive features may not work.
Tip: If shell transfer works but is slow, try enabling compression in SSH settings.
